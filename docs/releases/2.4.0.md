# CathoScroll 2.4.0

Status: release preparation on PR #40. This document is not evidence that the release has been published or deployed.

## Analytics and privacy

- Removes anonymous topic and Top Comments engagement collection, including browser clients, API ingestion, retry queues, native SQLite storage, database tables/functions and scheduled cleanup.
- Removes anonymous sponsor measurement, visitor/session frequency records, served events, served counters and campaign/day delivery totals.
- Clears pre-release signed-in analytics outboxes and derived Personalisation caches once on upgraded native installs so old consent grants cannot replay queued events.
- Sponsor placements remain available to signed-out visitors and signed-in users who have not opted into Sponsor measurement. Unmeasured selection creates no analytics event, receipt, counter, session identifier or frequency record.
- Service improvement analytics is an optional, explicit, signed-in choice covering topic and Top Comments engagement and site performance.
- Sponsor measurement is a separate optional, explicit, signed-in choice. It records only qualifying viewable sponsor impressions, clicks after viewability, bounded active viewing duration and frequency for users who opted in.
- Native analytics queues are limited to opted-in signed-in events. Android and Electron store those queues in encrypted, account-scoped app-private storage, bounded to 2,000 events per stream and seven days. Acknowledged events are deleted; withdrawal and account changes clear the relevant queues.
- Existing accounts are reset to no current choice for Service improvement analytics, Sponsor measurement and Personalisation. Analytics consent version 3 and Personalisation consent version `2026-11-22-v7` invalidate pre-release local grants and encrypted native personalisation caches, including while a device is offline. Fresh choices are required before optional collection resumes. The reset removes historical analytics and derived personalisation data while preserving consent-history evidence and product records such as likes, bookmarks, comments, progress and notes.
- There is no first-visit analytics consent popup. Users manage their choices in Account settings.
- At signup, unticked optional choices remain undecided: no current consent row or refusal-history record is created unless the user explicitly opts into at least one purpose.
- Personalisation remains separate and optional, off by default. Enabling it automatically enables Service improvement analytics, which remains enabled while Personalisation is active; users may also enable Service improvement independently. Users must turn off Personalisation before withdrawing Service improvement analytics. Passive reading signals contribute to recommendations only while Personalisation is enabled.
- Consent changes are account-bound and synchronised. Withdrawals immediately disable the affected local stream and clear its queued events; stale or offline choices are reconciled with authoritative server consent.

## Feed, comments and sponsors

- Keeps the shared feed renderer and the existing topic, Top Comments and sponsor card experience.
- General feed ranking uses public product interactions, curated order, recency, category exposure balancing and permitted signed-in Service improvement aggregates. It does not use anonymous analytics or sponsor activity.
- Sponsor selection for users without measurement consent remains unmeasured. Opted-in sponsor events require a server-issued placement receipt; clicks require a qualifying viewable impression.
- Sponsor reporting is limited to the opted-in measured population. It must not be represented as total delivery, total reach or all-visitor CTR.
- Admin analytics, topic/category drill-downs and sponsor reporting no longer expose anonymous engagement or served-delivery metrics.

## Database

- The clean-install schema is `docs/cathoscroll-database-bootstrap.sql`.
- Existing production databases must run the single-transaction `docs/cathoscroll-production-upgrade-2.4.0.sql` bundle. The two component SQL files are retained for review only; do not execute them separately.
- No Supabase migration files are used for this release. Do not run the clean-install bootstrap against production.
- Back up the database before the coordinated upgrade. The current Supabase project is on the Free plan and has no automatic daily backups, so a verified off-site manual database dump is a hard precondition. Apply only the canonical `docs/cathoscroll-production-upgrade-2.4.0.sql` bundle immediately before deploying the matching application. Do not execute the component files separately or leave the old application running against the upgraded schema.
- The canonical single-transaction SQL bundle (both component scripts in order, including the final signup trigger, consent-version changes, idempotent reset marker and admin analytics corrections) was executed twice against the current production schema inside one rollback-only transaction. Between runs, a new analytics grant, a later-version Personalisation grant/profile and an analytics event were inserted; the second run preserved them. Assertions also verified removal of legacy anonymous tables and served-count columns and presence of the release reset marker. The entire transaction was rolled back; production remains unchanged.

## Native applications and updates

- Android and Electron use the shared native application pages and account/feed experience.
- Android release APKs are signed using the existing long-lived Android release keystore. The release workflow derives the Android version code from the semantic version; for 2.4.0 this is `2004000`.
- Android checks the latest published stable GitHub release and offers the matching `CathoScroll-2.4.0.apk`. Download and installation remain subject to Android's package-install permission and confirmation.
- Windows and Linux AppImage Electron builds use `electron-updater` and the GitHub release metadata.
- Linux DEB installations and unsigned macOS builds use a version-check notice linking to the download page; users install those updates manually.
- The release workflow builds Windows x64, Linux x64 (AppImage and DEB), macOS Universal (DMG and ZIP), and the signed Android APK. It verifies the expected artifacts before publishing the GitHub release.
- Root and Electron package versions are `2.4.0`; Android release version name is `2.4.0`.

## Validation and release acceptance

- The exact-head GitHub Actions run must pass unit tests, ESLint, TypeScript, the production Next.js build, Android APK compilation and all Windows/Linux/macOS packaging checks.
- Dependency vulnerability audit, secret scanning and CodeQL must pass.
- The release workflow downloads the latest published APK and compares its signing-certificate SHA-256 fingerprint with the new APK. A mismatch blocks publication by default; the one-time workflow-dispatch override is only for an intentional signer transition and means existing Android installs must uninstall/reinstall.
- Verify Android update detection, download, resume and installation on a physical device.
- Verify Windows/Linux automatic update detection and installation, and the macOS manual update notice.
- Verify native offline analytics queue persistence, force-close/relaunch/reconnect, acknowledgement deletion, retry and withdrawal/account-switch cleanup on Android and Electron.
- Verify feed navigation, offline ranked-page fallback, Personalisation expiry/withdrawal, sponsor selection and receipt-bound event recording on physical native builds.
- After the coordinated database upgrade and website deployment, verify production feed, Account consent, sponsor delivery, admin analytics and native synchronisation against the upgraded schema.
- Complete controller approval of the privacy assessments, processor terms, international transfers, ICO fee position and applicable PECR treatment before distribution.

This is a release checklist and change summary. A passing CI run does not replace physical-device testing, production verification or controller/legal approval.
